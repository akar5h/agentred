## 3 · Architecture decisions (Days 1–4)

| Decision | Picked | Alternatives | Why |
|---|---|---|---|
| Day 1–2: auth representation | `MCPClient(bearer=str, headers=dict, auth_override=str)`. Bearer maps to fastmcp's `Client(auth=str)`; headers go via `StreamableHttpTransport(headers=...)`. | Construct a custom `httpx.Auth` subclass per probe. | fastmcp already gives us a clean shorthand for the 90% case (bearer). Avoiding custom auth classes keeps the wire format predictable for ops. |
| Day 1–2: side-effect taxonomy | Binary `safe | unsafe`, default unsafe. | 4-level (none/low/medium/high); tag-based (`[reads, writes, network, fs, ...]`). | Operators can reason about binary. Anything more granular would create a "what does medium mean for this server" debate without a clear runtime payoff yet. |
| Day 1–2: auth-failure probes | New `surface: auth`, separate code path that opens a fresh client per probe. | Fold into `tool_call` and use a special marker. | Auth probes need to override credentials *before* the handshake. Sharing the scanner's main client wouldn't allow that. The clean split matched the user's choice when asked. |
| Day 3: cross-tenant probe shape | Two-phase (A, B) with template tokens `{cred_a}`/`{cred_b}`/`{foreign_id}` threaded into payload arguments — NOT into HTTP bearers. | `--bearer-a`/`--bearer-b` as HTTP headers. | ch01 (Asana lab) authenticates via tool-argument `api_key`, not HTTP bearer. Many commercial MCPs do the same (workspace_id, account_id, customer_id). Template tokens generalize over both — operator writes the YAML to thread them wherever the server expects them. |
| Day 3: phase_a is a sanity check, not just an audit trail | Required to succeed; if it fails, finding is `error` not `pass`. | Make phase_a optional / advisory. | If A can't read A's own object, the operator's `--foreign-id` is wrong or `--cred-a` is invalid. A `pass` verdict in that situation would be silently wrong. Better to error loudly. |
| Day 4: when corroboration runs | Implicit, conditional on `matcher.kind == "marker_echo"` AND `corroborate` field present. | Always on; opt-in via `--corroborate` CLI flag. | Per-probe declaration in YAML keeps the contract local to the probe. Operators don't have to remember which flags to set per scan; the library author chose. |
| Day 4: verdict aggregation | Use the per-call `marker_outcome` (`vulnerable`/`echo`/`pass`) from the existing matcher, NOT raw `fired` booleans. Negative call adds context only. | Verdict purely from "did real markers fire and negative didn't fire". | Discovered live during ch08 smoke. The naïve "negative didn't fire" rule misclassified ch08 vulnerable as `echo` because git's `init_bare_repository` creates a directory named after literal input (so the negative payload reflects too — but the real payload still shows shell expansion in the response). The fix uses the matcher's per-response shell-syntax check, which already understood the distinction. See §5.2. |

### 5.2 The corroboration save on ch08

The most instructive finding from Days 1–4 was **what almost went
wrong** on Day 4's first smoke against ch08 vulnerable.

The corroboration verdict ran 3 calls per matched tool:
- `real_1`: `x$(echo JAKK-MARKER-A)` → response `Initialized repo at /tmp/xJAKK-MARKER-A/`
- `real_2`: `x$(echo JAKK-MARKER-B)` → response `Initialized repo at /tmp/xJAKK-MARKER-B/`
- `negative`: `xPLAIN-CANARY-C` (no metacharacters) → response `Initialized repo at /tmp/xPLAIN-CANARY-C/`

First aggregation rule was "vulnerable if both reals fired and
negative didn't". By that rule, all three reflected → verdict was
`echo`, NOT `vulnerable`. But ch08 IS vulnerable (the FLAG{} canary
came out via `secret_file_read`). The aggregation rule was wrong.

The fix: use the per-call matcher's existing shell-syntax check. For
`real_1`/`real_2`, the response contains the marker WITHOUT the
surrounding `$(echo …)` syntax → matcher classifies as `vulnerable`.
For the negative, response contains the marker but there was no
syntax to begin with → matcher classifies as `vulnerable` too, but
that's uninformative (the negative had nothing to expand). Verdict
rule: trust real_1 + real_2 outcomes; use negative for context only.

**Lesson:** A control payload only disambiguates a vulnerability if
the tool's normal behavior is to *reject* malformed input. For tools
that accept anything (write-anywhere, mkdir-arbitrary, etc.), the
negative reflects too, and the only signal is whether the real
payload's *interpretation* shows up in the response. That's what the
per-call shell-syntax check measures.

### 5.3 The `echo` finding on ch01

Running the corroborated `shell_marker` against `fetch_project` on
ch01 vulnerable produced outcome=`echo` (not `vulnerable`). This is
correct: `fetch_project(project_id, …)` doesn't shell out — it does a
JSON lookup. The probe sent `x$(echo JAKK-MARKER-…)` as the project_id,
the server returned a "not found" error containing the literal string,
matcher saw `$(` in the response window, classified each real call as
`echo`, verdict aggregated to `echo`.

**This is the matcher refusing to claim a finding that isn't real.**
ch01's actual vulnerability is cross-tenant authz, which `mcp.authz.
cross_tenant_read` correctly catches (vulnerable). If the shell_marker
probe had said vulnerable here, it would have been a false positive
that wasted operator triage time.

### 5.4 What the auth-misconfig probes catch (and don't)

All three breach-to-fix lab containers run with no HTTP auth. So
`mcp.auth.no_credential` and `mcp.auth.invalid_token` fire `vulnerable`
on every variant — including the *secure* ones. This is **honest, not
a false positive**: the labs are intentionally open. In production
the same probes would `pass`.

The implication: auth probes are most useful against servers that
*should* be authenticated. Against intentionally-public servers they
produce true positives that aren't actionable. Documented in the
per-test pages (`mcp.auth.no_credential.md` recommends flipping
`auth_override.expect_success: pass` in a local override for known-
public targets).

### 5.5 What the authz probe required, and didn't

Required:
- A target that exposes a tool whose argument list includes both an
  object identifier AND an identity claim (api_key, workspace_id,
  account_id, …).
- The operator to know two valid identities and one object identifier
  belonging to A's tenant.

Did NOT require:
- HTTP-bearer auth (despite our initial assumption — see §3 row "Day 3").
- Any matcher beyond `regex` / `substring` on the leaked tenant field.
- A "create object" tool. The probe is read-only; ch01 has no create
  primitive and that wasn't a blocker.

The two-credential machinery generalizes: any commercial MCP where
the server accepts a per-call identity argument and a per-call
resource identifier is a candidate target, regardless of how the
HTTP-level auth is implemented.

## 6 · Open design questions (carried forward + new)

From the v0.1 discovery doc that *remain* open:
- §6.1: schema-based vs name-based `applies_to` — no live data yet that name-based misses (deferred).
- §6.2: probe fan-out cap — still no targets with >2 matching tools.
- §6.4: where authz testing lives — **partially answered**. The two-phase probe shape works; remains to be seen if it generalizes to a third-credential or multi-step flow (e.g. Slack OAuth scopes).
- §6.5: jakk → grafted StrategicMemory seed — not done.

New questions raised by v0.2:
- **N1**: should `shell_marker`-class probes auto-fill non-first required args? With what values? Probably the answer is per-target, but a "best-effort dummy fill" might cover the common case.
- **N2**: should the auth-misconfig probes have a `--expect-auth` flag that defaults their `expect_success` to `pass` for explicitly-authenticated scans? Reduces operator overhead of declaring "yes I know this server has auth, don't fire on every public read".
- **N3**: how does corroboration interact with rate-limited targets? Three calls per probe is fine for `:localhost` and likely fine for GitHub MCP, but a server with a 1-rps limit would see noticeable scan duration growth. Could land an exponential-backoff layer, but only when the data justifies it.

## 7 · Patterns confirmed / new patterns

From v0.1 §7, all still hold. New from v0.2:

**7.6 Per-call matcher outcomes beat aggregate-call booleans.** The
verdict-aggregation save (§5.2) showed that throwing away per-call
classification information to aggregate on raw `fired` booleans is a
loss. Matchers should produce structured outcomes, not just true/false.

**7.7 Template tokens in YAML > new CLI flags per concept.** Day 3's
`{cred_a}` / `{cred_b}` / `{foreign_id}` could have been `--bearer-a`
/ `--bearer-b` flags wired into headers, or new fields per surface,
or per-probe configuration. Template tokens kept the surface area
small and generalized over HTTP bearer + tool-arg credential cases
in one shape.

**7.8 Honest skipped > pretended pass.** Auth probes that can't run
(missing `--bearer`) → `skipped`. Authz probes missing `--cred-a` →
`skipped`. shell_marker on a tool with no string arg → `skipped`.
The `skipped` outcome is a feature, not a defect. Operators
auditing a scan want to see "we tried but couldn't" separately from
"we tried and it passed".

## 11 · C+ — schema-aware argument-kind resolution (2026-05-23)

Added after the GitHub-MCP-target discussion surfaced that v0.2's
probes wouldn't generalize. This is the v0.1 §8.7 "schema-shape
applies_to" item, designed concretely.

### The problem it solves

v0.2 probes inject via `__first_string_arg__` — the *first* string-typed
argument by schema order. That works when the targetable arg is first
(breach-to-fix's `read_file_contents(file_path)`) but fails on
multi-arg signatures where it isn't:

```
GitHub: get_file_contents(owner, repo, path, ref)
                          ↑ position 0 is owner, NOT the path we want
```

Filling `owner` with a traversal payload errors out (missing required
`path`) → `error` outcome, not a real probe. This blocked jakk from
meaningfully scanning GitHub MCP (and most real-world servers, whose
tools take 2-4 args).

### The design

A probe declares the *semantic role* of the arg it wants
(`target_arg_kind: path`); the scanner resolves the role to the actual
arg name per-tool via `applies.ARG_KINDS`:

- Pass 1: first string arg whose **name** matches the kind's name-regex.
- Pass 2: first string arg whose **description** matches the desc-regex.
- No match → tool filtered out at `applies.matches()`, probe `skipped`.

Five kinds registered: `path`, `query`, `id`, `url`, `text`. No
`command` kind — shell-injection has no schema clue, keeps
`__first_string_arg__`.

Payload uses `__target_arg__` (role-based) instead of
`__first_string_arg__` (position-based). Both coexist; existing probes
unchanged.

### What generalizes now

The same `mcp.path.*` probe fires correctly against:
- GitHub `get_file_contents(owner, repo, path, ref)` → `path`
- breach-to-fix `read_file_contents(file_path)` → `file_path`
- breach-to-fix `list_directory_contents(full_path)` → `full_path`
- any future server's path tool, by name or description

Zero per-vendor YAML. One library, all servers.

### Validation

- **110 unit tests** (was 75 in v0.2 Day 4; +35 for arg-kind + target-arg resolution).
- **Live multi-arg validation**: a local `read_file(owner, repo, path)` server proved `__target_arg__` lands in `path` while `__first_string_arg__` lands in `owner` — the exact GitHub-shaped case, end-to-end through jakk's scan code.
- **6-endpoint regression sweep**: identical to the pre-C+ baseline after one fix.

### The regression C+ nearly shipped with

First implementation broke ch02. The `path` name-regex used `^path$`
and `file_?path`, neither of which matches `full_path`
(`list_directory_contents`'s arg). So `target_arg_kind: path` *excluded*
that tool — `prefix_bypass` dropped from 2 findings to 1 on ch02. The
6-endpoint sweep caught it (12 rows → 11, 5 vuln → 4).

Fix: broaden the `path` name-regex to match `path` as a substring
(covers `full_path`, `file_path`, `filepath`, `dir_path`) with anchored
matches for standalone words (`^file$`, `^dir$`) to avoid false
positives like `profile`. Pinned with a parametrized test including
`full_path`, `dir_path`, `absolute_path`, `relative_path`.

**Lesson (again):** the value of the 6-endpoint smoke isn't proving the
happy path — it's catching the regression that 110 green unit tests
didn't, because the unit tests used the arg names the author thought of
(`file_path`) not the one the real lab used (`full_path`). Test against
the real tool surface, not the imagined one.
